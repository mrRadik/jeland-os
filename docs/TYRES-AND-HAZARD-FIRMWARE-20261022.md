## Температура: от найденной формулы к источнику

Ранее извлечённая `sva.cluster` — ARM64 QNX/Kanzi. Штатный `RcDataRecThread_TPMS` читает `/tmp/pps/spi_service/a005?wait,delta`, тип сообщения 8. `RcDataPPSGeneralDecoder` берёт JSON-массив `data` и копирует байты в `RcDataSet`. `RcDataMgr::getBcm5` читает первые 8 байт этого сообщения.

В `RcMVehicleInfoTPMSUpdate`:

- буфер BCM_5 находится на стеке по `x29+0x80`;
- `byte[2] & 3` выбирает колесо; таблица переходов по 0x87d0d8 для ветви 0x1a99fc;
- 0 → 0x1aa6e0 / FrontLeftTempValueStr, 1 → 0x1aa680 / FrontRightTempValueStr;
- 2 → 0x1aa618 / RearLeftTempValueStr, 3 → 0x1aa740 / RearRightTempValueStr;
- значение температуры берётся из `byte[3]` (загрузка с `x29+0x83`).

Статусы: LF=`(b0>>1)&7`, RF=`((b0&1)<<2)|((b1>>6)&3)`, LR=`(b1>>3)&7`, RR=`b1&7`. Нативный обработчик исключает raw 0xff и статус 6. В Jeland OS дополнительно не публикуется зарезервированный статус 7.

`RcMVehicleInfoTPMSTireTemperatureValueUpdate` по адресу 0x1a6d78 применяет константы double 0.65 и -40 (0x1a6ff0/0x1a6ff8) и signed `fcvtzs`, то есть для °C: `int(raw * 0.65 - 40)` с усечением к нулю. В другой вспомогательной функции используется unsigned conversion; в приложении воспроизведён основной update-path, сохраняющий отрицательные температуры.

Это не формула для CarInfo/140: там четыре давления, а не пакет BCM_5. Их значения не используются вместо температуры. В имеющемся Android SDK найдено давление и предупреждения/единицы, но не подтверждённый отдельный getter четырёх температур.

## Новый канал в Jeland OS

Из реального Probe 0.20 подтверждено соединение `eth1 / 192.168.8.2 -> 192.168.8.1:8000`. Протокол сервиса на машине пока не опознан — его поддержку нельзя выводить из одного connect.

Реализован ограниченный клиент qconn:

1. Проверяет QCONN greeting, версии broker/file >=256, подтверждение переключения только на `service file`.
2. Разрешает единственный путь `/tmp/pps/spi_service/a005`, единственный режим открытия O_RDONLY=0.
3. Читает один snapshot до 2048 байт, закрывает дескриптор. Без `?wait`, создания/перезаписи файлов, launcher, shell, debugger, upload, chmod или выключения защит.
4. Валидация размера/типа/имени файла, дескриптора, ответа протокола, PPS-объекта и восьми байт. Неизвестный формат не отображается как температура.

Чтение начинается только при foreground + VEHICLE + подключённом CarInfo. Отдельный executor, климат не блокируется. Только внутренний Ethernet 192.168.8.2/24; фиксированный peer 192.168.8.1:8000, без DNS, Wi-Fi, USB-модема, VPN или Интернета. Тайм-ауты, отмена/закрытие сокета при уходе в фон, retry не чаще чем раз в 30 секунд при отказе. Период нормального чтения 700 мс; кеш каждого колеса отдельно истекает через 30 секунд. DEMO и реальные значения не смешиваются.

Температуры подаются в существующие карточки и окно колеса. Новых карточек, ресурсов приборки и управляющих команд не добавлено. Давление осталось на прежней калибровке.

Важно: это функциональный новый read-only источник, но получение ответа qconn/PPS и совпадение показаний с приборкой **ещё не проверены на автомобиле**. Пока нельзя говорить, что четыре температуры уже заработали. При отказе остаётся «Нет данных», причина — в журнале `TPMS_QNX_*`.

Справочные первичные источники:

- Протокол read-only file service исследован по исходному клиенту автора: https://github.com/zayfod/qcl/blob/master/qcl.pl (MIT, Kaloyan Tenchov, 2009–2014). В приложение не включены его функции запуска, записи/удаления или изменения прав; реализация на Kotlin самостоятельная.
- По документации QNX PPS обычное открытие без `?wait` даёт неблокирующий snapshot: https://qnx.com/developers/docs/7.1/com.qnx.doc.pps.developer/topic/subscribe_notification_filedescriptor.html

## Что дополнительно разобрано для аварийки

Из того же обновления восстановлен `vendor.img`: 374743040 байт, SHA-256 `0e492b67b956ea147fd366840be8f823949edec4e08f53f2b2c82755ed44be98`; проверен по OTA. Извлечены релевантные обычные файлы Ext4, без монтирования образа и запуска программ.

Исследованы:

- `/emmc/sva/bin/sva.avm`, символы RcDataSend и обработчики TurnLight;
- `libdesaysv_vehiclehal.so`, `libdesaysv_vehicledevice.so`, remote.spi2ethenet, libcanwrapper/libcantranslator;

- OEM Java CarInfo SDK и конфигурация аппаратных кнопок;
- `mcu.zip`, `radio.bin`: Motorola S-record, проверены контрольные суммы всех 7181 S3-записей (919154 байта полезных данных), выполнен поиск читаемых диагностических строк. Это не полный разбор машинного кода MCU.

Результат:

- `ReadOnlyID.ID_HAZARD_LIGHT=79` — обратное состояние, не команда включения.
- `AvmID.ID_REQ_HAZARD_LIGHT=24`, модуль AVM 0x50008 — ранее известный кандидат. Значения 0/1/2 уже проверялись без физического эффекта; новая расшифровка допустимых значений не найдена.
- `RcAVM_AvmCarTurnLightSet`, `AvmAppModel::SetCarTurnLights` в QNX управляют моделью автомобиля AVM: цепочка идёт в AvmPresent/поля модели/update_car_set_value, это не доказанный setter физических ламп.
- В стандартном Vehicle HAL присутствует emulated/fake-data код. Само наличие AAOS HAZARD_LIGHTS_SWITCH в конфиге не подтверждает его связь с MCU. На машине этот путь до SET не дошёл из-за отсутствия системных разрешений, поэтому физический результат через AAOS остаётся неизвестным.
- Доступная безопасная управляющая команда аварийки из обычного приложения пока **не установлена**. Новые случайные CAN/RAW SET не добавлены. Системные разрешения/файлы/службы автомобиля не менялись.
