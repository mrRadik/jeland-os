# 0.9.28 — первый этап автоматизаций: подтверждённое движение

23 октября 2026. code69 / 0.9.28-automation-trips, min30 / target35.

## Объём и важная граница

По прямому выбору пользователя событием служит начало движения. Открытие
Activity, пробуждение, работа двигателя, подключение Binder и загрузка
правил не вызывают автоматических действий.

Реализованы движок определения начала поездки, отдельный read-only адаптер
штатной скорости и переключатель в разделе автоматизаций. Это **shadow
проверка**, а не завершённое LIVE-управление комфортом. Существующий
AutomationEngine/MockAutomationActionExecutor остаётся изолированным.
Новый монитор не вызывает его, не выдаёт MOCK за физический результат,
не передаёт SET и не меняет реальные сиденья/климат/шторку. Это прямо
написано в интерфейсе. Нет новых permissions или foreground-службы.

## Подтверждение движения

AutomationTripGate — Android-free. Сначала достоверная остановка <=0,2 м/с.
Первый запуск приложения уже в движении оставляет WAIT_STOP. Затем модуль
скорости >=1,5 м/с (5,4 км/ч), минимум три независимых значения с суммарной
длительностью >=2500 мс; промежуток между ними <=1500 мс. Задний ход тоже
является движением. Малый ход, единичный скачок, NaN/Infinity/модуль >100,
старые/будущие и повторные timestamps не подтверждают поездку.
Пауза/отсутствие связи/разрыв ряда сбрасывают неполное подтверждение и требуют
новой остановки, но не очищают уже подтверждённую поездку.

Trip ID сохраняется ДО публикации события. AndroidSettingsStore получил
отдельный DurableSettingsStore.putDurable с commit/проверкой результата;
обычные настройки по-прежнему apply. Ошибка сохранения не выдаётся за старт.
Остановка на светофоре не сбрасывает ID, новый процесс читает тот же ID.
Только OEM SLEEP=26 / STR=40 либо изменение известного boot count
сбрасывают поездку. DISPLAY_OFF, пауза, отключение связи и тайм-аут не
считаются выключением автомобиля. При недоступном конце поездки повторный
старт консервативно блокируется, а не угадывается по времени простоя.

## Штатный источник, что известно и что ещё проверить

Локальные APK-источники:

- `work/field-20261018-afternoon/carplay-jadx/sources/q1/j1.java`:
  подписка 519, чтение DoubleVector[0] как скорости (VehicleDataImpl).
- `work/engmode-jadx/.../VDServiceDef.java`: системный
  com.desaysv.ivi.vds.vehicle.service.VehicleService, IVDBus.
- `work/system-jadx/carstate/.../vdb/VdbManager.java`: POWER_STATUS=196609,
  поле status = текущий power mode; CarStateService публикует тот же формат.
- PowerStateController: режимы SLEEP=26, STR=40 (не просто выключение экрана).

VHAL PERF_VEHICLE_SPEED имеет младший ID 0x0207=519 и стандартные единицы
м/с; [AOSP определение](https://android.googlesource.com/platform/hardware/interfaces/+/refs/heads/main/automotive/vehicle/aidl_property/android/hardware/automotive/vehicle/VehicleProperty.aidl).
Это основание для адаптера, **не полевая калибровка OEM-реализации**.
Поэтому прежде любых автоматических SET нужны реальные логи данного канала.
Данные INFO/119 и противоречивые RPM не переводятся в скорость по гипотезе.
GPS, replay навигации и DEMO-значения в детектор не входят.

Адаптер делает начальный GET (он может подтвердить только остановку),
затем слушает сообщения. Для скорости требуется точный event 519,
single DoubleVector, отсутствие IS_NULL и eventTime не старше 3 с и не
в будущем. Пакеты без timestamp не объявляются свежими. Обработка также
проверяет задержку до main-потока. ГУ/связь/foreground обязательны.
Обычные app-lifetime подписки один раз на Binder: не пересоздаются для
каждого сообщения. У текущего IVDBus нет метода удаления общей subscribe;
после выключения проверки callbacks инертны, жизнь заканчивается с процессом.
CarState binding сохранён для read-only события сна, пока жив процесс;
оно может не прийти, если OEM заранее убьёт процесс. Тогда нет сброса/повтора.
Нет периодического опроса, wakelock или открытия Activity.

Настройка проверки отдельная и default-off. Existing rules/Room schema v1
не мигрировались и не удалялись. Debug-кнопки MOCK остаются явно тестовыми.

## Диагностика и проверка

AUTOMATION_TRIP: фазовые переходы, trip ID и shadow_only=true /
actuator_commands=0. AUTOMATION_SPEED: исходная скорость и timestamps,
не чаще одного раза в секунду; одинаковые сообщения состояния не дублируются.
Журнал прежний JelandOS_vehicle_*.log, выгрузка START → L.

artifacts/portable. Затем целевые testDebugUnitTest:

  запуск уже на ходу, устойчивое движение/однократность, светофор,
  переподключение/новый процесс, sleep/boot, скачок/малый ход, разрыв,
  старые/будущие/некорректные данные, дубли timestamp, задний ход,
  ошибка durable commit.
- AutomationEngineTest — 17 прежних тестов, PASS (MOCK/claim/arbitration).
- assembleDebugAndroidTest — успешная компиляция; инструментальные UI

- aapt подтверждает code69/name0.9.28. Синтаксис portable-скриптов проверен;

На машине до выезда: установить 0.9.28, открыть «Автоматизации», включить
«Проверять начало поездки» в режиме ГУ. На месте ничего не должно
подтверждаться. Во время обычной поездки с экраном ничего делать не нужно.

приход SLEEP/STR. Исполнение комфорта намеренно остаётся следующим этапом.
