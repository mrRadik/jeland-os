# Автоматизации Jeland OS — 0.9.33

## Реальное управление

Рабочий AppContainer использует LiveAutomationActionExecutor и общий
DesayCarSession, а не MockAutomationActionExecutor. Тестовой поездки/подставных
показаний в пользовательском разделе больше нет. DEMO не отправляет команды.

Каталог: водительское и переднее пассажирское сиденья (подогрев/вентиляция),
заднее левое и правое (подогрев), руль (включить подогрев), шторка (открыть
полностью/наполовину). KEEP сохраняет режим, OFF явно выключает. Нагрев и
вентиляция одного переднего сиденья взаимоисключаются; разные сиденья независимы.

## Условия и событие запуска

У каждого сценария — имя, устройства/действия, приоритет и способ запуска:

- Вручную: только выбранный сценарий по кнопке. Условия температуры и события
  не проверяются, но сохраняются проверки связи, свежести и безопасности.
- По температуре: строго ниже/выше заданного порога, только при выбранном событии.
- Без температурного условия: при выбранном событии.

Событие выбирается отдельно в каждом автоматическом сценарии:

1. При запуске двигателя — для прогрева, без ожидания движения.
2. После начала движения — остановка, затем устойчивое движение от 5,4 км/ч
   минимум 2,5 с / 3 независимых сообщения OEM 519. GET движущегося автомобиля,
   GPS и открытие приложения на ходу не запускают сценарии.

Новые черновики по умолчанию используют ENGINE_START. Старые правила при
миграции остаются MOVEMENT. Менять событие можно независимо от температуры,
с сохранением после перезапуска. Ручной режим не стирает этот выбор.

Общий переключатель автоматического запуска включён по умолчанию для новой
реальной интеграции (отдельный ключ automation.live.enabled). Выключение
отменяет автоматические задания, не запрещая ручной запуск. Выключенный
автозапуск конкретного сценария не запрещает его ручную кнопку.

## Источники

Двигатель: read-only INFO 0x50004/74, OEM ID_ENGINE_STATE. В источниках
ReadOnlyID.java он называется состоянием двигателя. Лог Probe 19 октября
09:45 показывает /74=0 вместе с /13,/14=0 и последующим нулевым /62;
при запуске /13 проходит 2,3,4, /74 становится 1, /62 снова ненулевой.
Два разных свежих чтения /74=1 с интервалом от 1 с подтверждают работу.
При штатном опросе 5 с это обычно вторая итерация. RPM*4 не используется.

Первое подключение к уже работающему двигателю тоже может подтвердить текущий
цикл; точного времени физического пуска эти данные не дают. Сохранённый ID
не допускает повтора при onResume/новом процессе/переподключении. Start-stop
или заглохший двигатель при включённом зажигании не переоткрывают цикл.
Подтверждённые /74=0 и /13=0 в двух чтениях (от 1,5 с) либо OEM SLEEP/STR
сбрасывают цикл. Неизвестное значение или ошибка durable commit не запускают SET.

Температура: только OEM HVAC /19 * 0,5 - 55. Исходный возраст показания
сохраняется; для реальных сценариев лимит 15 с, не 5 минут и не DEMO-погода.
Нет свежего значения — температурный сценарий пропускается целиком.

## Исполнение

Перед первой записью на общем worker читаются все необходимые устройства.
Проверяются активный foreground, реальная связь, разрешённые записи,
epoch подключения, доступность/возраст показаний, диапазоны и конфликты.
Используется существующий VerifiedVehicleProtocol: сиденья /95,/96,/93,/94,
/139,/141 (SET level+1), руль /160, шторка VR /124. Новых произвольных OEM SET нет.

Руль /160 — toggle: если уже включён, не отправляем ничего. Непосредственно
перед SET он перечитывается; автоматического повтора нет. Выключение другого
режима сиденья идёт перед включением нового. Искусственных пауз между SET нет.

Шторка не имеет прикладной блокировки по скорости или требованию стоянки:
оба события ENGINE_START/MOVEMENT и ручной запуск допускаются. Скорость
не передаётся ни в планировщик команд, ни в исполнитель шторки. Отдельный
опрос скорости для такой проверки удалён; детектор события движения сохранён.
Связь и свежее состояние самой шторки по-прежнему обязательны. Если сама
шторка уже открывается/закрывается или недоступна, весь сценарий не отправляется.

После SET через 1,2 с читается обратное состояние. Статусы различают:
CONFIRMED (GET совпал), SENT (точное положение HALF не измеряется),
UNCONFIRMED, PARTIAL/INTERRUPTED. Binder-ответ не выдаётся за подтверждение.
При потере связи/паузе/сне/отключении автоматики отправка прекращается.
Запрос, который мог дойти до автомобиля, не повторяется вслепую.

Preflight всего сценария — до первого SET. Физические SET НЕ атомарны:
если ошибка возникла после начала отправки, часть действий могла выполниться.
Отменять их обратными командами автоматически нельзя; журнал показывает
неопределённость/частичную отправку, а не выдуманный rollback.

## Один раз и конфликты

Room фиксирует session ID, снимок сценариев и PENDING до выполнения.
Engine-start и movement имеют разные сессии и выбирают только свои правила.
Повтор ID не переигрывается после рестарта. Если событие уже было, новый
или отредактированный сценарий сам по себе не запускается задним числом.

Внутри события побеждает приоритет, потом updatedAt, потом UUID.
Проигравший при пересечении устройства пропускается целиком. Разные сиденья
не конфликтуют. Правила двигателя и движения не конкурируют между собой:
они намеренно относятся к разным событиям.

## Хранилище и ограничения

Room v4. Миграции 1→2→3 сохранены; 3→4 добавляет launchEvent=MOVEMENT
правилам и указателю сессии. ID, действия, журнал, даты, приоритеты остаются.
Destructive migration нет. Экспортированные схемы 1–4 сохранены.

Автоматизации работают при активном Jeland OS в режиме ГУ. Если ГУ спит и
приложение не запущено, удалённый прогрев сам по себе не запускает код Android.
Для работы при пробуждении нужен включённый автозапуск Jeland OS и фактическое
пробуждение/вывод приложения. Отдельный фоновый автомобильный сервис не добавлен.
