# Автоматизации Jeland OS 0.6.0

## Что реализовано

Отдельный пункт постоянного меню: Главная, Музыка, Навигация, Автомобиль,
Автоматизации, Приложения, Настройки. Старой вложенной вкладки в исходниках не
было. Переход «Автомобиль» в штатные настройки сохранён. Хедер, нижний климат,
другие экраны и их реальные команды не перенастраивались.

Правила изначально не создаются автоматически. Можно создать, отредактировать,
включить/выключить, удалить с подтверждением. Название после обрезки пробелов
обязательно, максимум 50 символов. Новые правила включены; выключенное правило
сохраняет активность при редактировании. Ошибка записи не выдаётся за сохранение.

Сиденья — один тип и один объект, шесть независимых параметров:
подогрев/вентиляция водителя и переднего пассажира, подогрев слева/справа сзади.
Режимы: KEEP/0/1/2/3. KEEP оставляет значение, 0 выключает. Нельзя сохранить
правило из одних KEEP. При выборе положительного уровня нагрева редактор явно
выставляет 0 вентиляции того же переднего места, и наоборот. Две положительные
установки одновременно запрещены валидатором. Если KEEP конфликтует с уже
активным противоположным режимом в модели, исполнитель отказывается от всего
правила без частичных изменений; KEEP не превращается в скрытую команду OFF.

Для сидений строгое «ниже»/«выше», включая отрицательные/дробные °C, диапазон
−60…+60. Равенство порогу не срабатывает. В первой версии отдельный ручной
mock-источник наружной температуры, не погода и не салонный климат. Изначально
температура неизвестна. Свежесть максимум 5 минут; будущая дата, пропуск, NaN и
устаревшее измерение не считаются подходящей температурой. Значения +5 в редакторе
и в тестовом поле — порог/ввод, не автоматически полученное измерение.

Шторка — отдельный компонент, только OPEN_FULL / OPEN_HALF. Ни температурного
условия, ни сидений, ни произвольных процентов. В MOCK проверяются связь,
доступность компонента, известность состояния, стоянка и разрешённость управления.
Если положение уже совпадает, результат «Изменения не нужны», лишней команды нет.

## Архитектура

- core/automation: типизированные AutomationRule/SeatsAction/SunshadeAction,
  AutomationValidator, AutomationRepository, AutomationEngine,
  AutomationSessionTracker, интерфейсы температуры/исполнителя и результаты.
- data/automation: RoomAutomationRepository, AutomationDatabase,
  MockAutomationTemperatureRepository, MockAutomationComfortRepository,
  MockAutomationActionExecutor.
- ui/automation: AutomationViewModel, AutomationEditorViewModel и отдельные
  AutomationsScreen/AutomationCard/AutomationEditorScreen/ComponentPicker/
  TemperatureTriggerEditor/SeatsActionEditor/SeatActionRow/SunshadeActionEditor/
  DeleteAutomationDialog/AutomationEmptyState. Черновик переживает сохранение
  состояния через SavedStateHandle, запись — только по «Сохранить».
- AppContainer: существующий DI, отдельная mock-ветка автоматизаций. Для тестов
  можно подставить изолированные Room и SettingsStore без изменения данных пользователя.

Используются существующие панели, типографика и изображения сиденья. Шторка —
программная градиентная иллюстрация с анимацией. Workflow/edit/delete — векторные
иконки того же семейства, без emoji. Все темы берутся из JelandTheme.

## Хранилище и расширение

Room 2.7.2, отдельная jeland_automations.db. Конфигурации действий — типизированные
столбцы/Embedded, не произвольный JSON. Маппер и валидатор проверяют соответствие
компонента payload, диапазоны, взаимоисключение и триггер. Таблицы: правила,
сессии, результаты и указатель текущей debug-сессии. UUID хранится как строка,
createdAt/updatedAt сохраняются; время изменения монотонно относительно всех
правил даже при сдвиге часов, чтобы политика последнего изменения была определена.
Переключатель и удаление адресуются по ID и не меняют остальные правила.

Схема версии 1 экспортируется в app/schemas/. Destructive migration не включена.
Новый компонент потребует типизированного payload, валидатора, редактора,
исполнителя и явной миграции, не переписывания движка/сессионного журнала.
История хранит снимок имени, статус, объяснение и сформированное описание команд;
этот текст никогда не используется для исполнения. Удаление правила не стирает
исторические результаты сессий. Документация зависимости:
[AndroidX Room](https://developer.android.com/jetpack/androidx/releases/room).

## Политика исполнения

AutomationEngine вызывается только явным событием новой сессии. Ни Activity,
ни открытие раздела/главной, ни onResume, ни загрузка правил не являются триггером.
Сейчас событие доступно только через debug-кнопки. Реальная поездка/зажигание не
детектируются, никакого WorkManager, расписания, boot receiver или сервиса нет.

До любой обработки одна Room-транзакция фиксирует уникальный ID сессии, снимок
активных правил и PENDING-записи. Второй движок/повторный вызов получает «уже
обработано». Это at-most-once: при аварийном завершении после фиксации, но до
результата, остаётся PENDING, а не выдуманный успех и не повтор команд.
Повтор после перезапуска процесса также заблокирован сохранённым ID сессии.
Не подходившие по температуре или безопасности правила потребляют эту проверку
сессии; автоматического позднего retry при появлении данных нет.

Конфликт решается для компонента целиком: больший приоритет 0…10, затем более
позднее updatedAt, затем стабильный UUID. KEEP победителя не заполняется из
проигравших сценариев. Если победитель не может выполниться, проигравший не
подставляется скрыто. Все пропуски/конфликты видны в журнале.
Редактирование/включение во время сессии влияет только на следующую сессию.
Ручное изменение модели после исполнения не перезаписывается повтором сессии.

## Строгая граница MOCK

MockAutomationActionExecutor принимает только MockAutomationComfortRepository.
У него нет IVDBus, CarInfoService, VehicleRouting, штатного SeatsRepository или
VehicleRepository. Уровни 0…3 — значения модели, не OEM-коды. Даже обычные
DEMO-репозитории нижней панели не меняются: вся симуляция видна в debug-панели.
При подключённом ГУ эта изоляция сохраняется. Новых permissions нет.

Модель комфорта/температуры сбрасывается при завершении процесса. Правила,
указатель сессии и история сохраняются в Room. Поэтому старый результат
«Выполнено в MOCK» не является текущим показанием автомобиля или восстановленной
модели и тем более не подтверждением физического результата.

Для будущего VDS нужен отдельный аудированный исполнитель: подтверждённые OEM
ID и ограничения, проверка свежего состояния перед каждым SET, разрешение записи,
безопасность шторки, обратная связь и отсутствие автоматических повторов.
Простого переключателя MOCK→LIVE в этой версии специально нет.

## Как проверить без автомобиля

1. Открыть «Автоматизации» → «Создать автоматизацию». Создать «Зимний комфорт»:
   сиденья, ниже +5 °C, нагрев водителя/пассажира 2, заднего левого 1,
   заднего правого KEEP. Сохранить.
2. Создать «Летний комфорт»: сиденья, выше +25 °C, вентиляция спереди 2,
   нагрев спереди 0, сзади KEEP. Сохранить.
3. Создать «Шторка при запуске»: шторка, открыть наполовину. Сохранить.
4. «Тестовая поездка · MOCK» → ввести 0 → «Применить» → «Новая сессия».
   Ожидаются зимнее правило и шторка, летнее пропущено. Ниже показаны результаты,
   сформированные команды и вся тестовая модель.
5. «Ручное изменение · подогрев водителя» → «Повторить текущую».
   Ожидается «Повторных команд нет», ручное значение сохраняется.
6. Ввести +30 → «Применить» → «Новая сессия». Вентиляция спереди 2, нагрев 0.
   KEEP заднего ряда оставляет прошлые тестовые уровни, не выключает их.
7. «Нет данных» или «Просрочить» → новая сессия: сиденья пропускаются. Шторка не
   зависит от температуры. «Движение» → новая сессия: шторка не выполняется.
8. Создать ещё одно подходящее правило сидений с более высоким приоритетом.
   Новая сессия выбирает его, проигравшее помечает конфликтом. Возврат приоритета
   к равному позволяет проверить политику последнего изменённого.
9. Выключить/изменить правило → повторить текущую сессию: новых действий нет.
   Новая сессия использует изменения. Закрыть/открыть приложение: правила на месте,
   повторить текущую всё ещё не выполняет команды.
10. Проверить «Отмена» в редакторе и подтверждение/отмену удаления.

Журнал последних результатов доступен в тестовой панели и хранится в Room.
Текущий START → L сохраняет прежние OS/Probe-логи, но отдельная автоматическая
выгрузка Room-базы/истории автоматизаций в этот ZIP пока не добавлена.
