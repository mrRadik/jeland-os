# 0.9.17 — запуск вместе с системой

Промежуточная версия: после выдачи APK запущено 8 прицельных Android-проверок, одна выявила отсутствие NEW_TASK (SystemStartupInstrumentation.kt:58). Остальные 7 прошли, включая UI в двух темах; снимки сохранены в screenshots/qa-0.9.17. Использовать исправленную 0.9.18. Упоминание NEW_TASK/RESET_TASK_IF_NEEDED ниже описывает намерение, но в самом APK 0.9.17 эти флаги отсутствовали: Intent.makeMainActivity их не добавляет.

22.10.2026. versionCode 58, versionName 0.9.17-system-startup.

В начале настроек добавлен раздел «Запуск приложения» и переключатель «Запускать вместе с системой». По умолчанию выключен. Значение хранится в существующем SettingsStore под system.autostart, независимо от оформления/настроек главной. Выключение сохраняется между запусками.

При включении без необходимого разрешения открываются системные настройки «Поверх других приложений» для Jeland OS. Пользователь выдаёт разрешение сам; при отказе переключатель сохраняет желание автозапуска, но интерфейс явно показывает, что разрешение ещё требуется. После возврата из системных настроек permission-state обновляется. Реальные overlay-окна не создаются.

Добавлены RECEIVE_BOOT_COMPLETED и SYSTEM_ALERT_WINDOW. Неэкспортируемый SystemBootReceiver принимает только BOOT_COMPLETED; не обрабатывает обновление APK, разблокировку, включение экрана или произвольные события. На загрузке сначала проверяются сохранённый opt-in и разрешение. Затем ровно один запрос нашего обычного MainActivity через MAIN/LAUNCHER + NEW_TASK/RESET_TASK_IF_NEEDED/SINGLE_TOP. Нет очистки истории, смены HOME, foreground-сервисов, таймеров повторов, wakelock, overlay-окон или команд автомобиля. Receiver не создаёт AppContainer и не подключает OEM-сервисы. Само приложение и его обычные подключения инициализируются только при открытии MainActivity.

Результат BOOT (DISABLED/NEEDS_PERMISSION/REQUESTED/FAILED) записывается в собственные настройки; при ручном открытии попадает в журнал OS. diagnostics.json дополнен startup.enabled/permissionGranted/lastBoot. REQUESTED означает принятие запроса startActivity, а не подтверждение видимости поверх OEM-лаунчера.

## Ограничения платформы и источники

Android ограничивает открытие Activity из фона; предоставленное пользователем SYSTEM_ALERT_WINDOW является одной из документированных разрешённых ситуаций: [официальная документация](https://developer.android.com/guide/components/activities/secure-bal#exceptions). BOOT_COMPLETED допускается в manifest как исключение из ограничений неявных broadcast: [официальный список](https://developer.android.com/develop/background-work/background-tasks/broadcasts/broadcast-exceptions).

Приложение нужно вручную открыть после первой установки и включить настройку. Речь о полной загрузке Android; выход ГУ из сна не является BOOT_COMPLETED. Принудительная остановка/ограничения OEM могут мешать доставке события или показу окна; обходов системной политики не добавлено. Штатный лаунчер, системные файлы и прошивка не заменяются. Проверка после настоящей полной перезагрузки конкретного ГУ остаётся необходимой.

### Прицельные проверки

Подготовлены 7 прицельных Android-проверок на подставном Context: default-off/повреждённое значение, сохранение настройки, только правильное событие, точный Intent нашей Activity, отсутствующее/отозванное разрешение, явный переход к системным настройкам, отказ платформы без повторов и приватность manifest entry. Отдельная UI-проверка переключает off → pending permission → ready → off в обеих темах. Никакие разрешения через ADB не выдаются и устройство не перезагружается. Полный набор старых тестов не запускается. Финальный результат записывается после исполнения.
