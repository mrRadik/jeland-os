## Мобильная сеть, Wi-Fi и Bluetooth

CarLan event 720899 / 0xb0003 выдаёт Parcelable VDNetworkStatus в ключе `info`.
Прежний код и фиктивный Binder ошибочно использовали `data`. Исправлены оба;
добавлен отрицательный тест старого ключа и IS_NULL. GET остаётся единственным
запросом к CarLan, без SET, subscribe или принудительного обновления модема.

OEM manager/b/a.b(TBoxNetworkStatus) перед созданием DTO переводит сигнал:
0–5 → 0, 6–11 → 1, 12–17 → 2, 18–23 → 3, 24–32 → 4.
Клиент НЕ применяет эту формулу повторно: принимает только готовые DTO 0–4.
Отдельный SignalStrength=26/28 из ConnectivityService — другой источник, он
не используется как число полосок. При свежем OEM-ответе с неизвестным уровнем
не подставляется Android-уровень чужого/виртуального телефонного модема.

В полевых дампах Wi-Fi выключен. Bluetooth включён, профили A2DP Sink и HFP
Client отключены. Эти конкретные состояния предыдущая версия читала верно.
Теперь BT ON без соединения светлый, ON + соединение голубой, OFF тусклый.
Тип активной мобильной сети выделяется акцентом. Ошибки регистрации наблюдателя
и получения BT-профилей теперь попадают в интеграционный журнал.
Новых разрешений, сканирования, pairing, подключения или интернет-загрузок нет.

## Климат: почему окно открывалось снова

На один пользовательский SET журнал содержит CLOSE_PANEL через 450, 1000,
1700 и 2500 мс и повторные OEM_OPEN. CLOSE_PANEL запускает только анимацию.
В штатном HvacContentView.n() после её завершения сохранённый флаг показа
может немедленно вызвать новое открытие. Поэтому удалён весь цикл таймеров,
receiver и HvacPanelCloseWindow, а не добавлены новые попытки закрытия.

Штатный HvacService CLOSE_HVAC_BT при активном климатическом флаге отправляет
HVAC /9 VALUE=[2]. HvacID называет /9 ID_AC_DISPLAY_ACTIVE; питание — другой
канал /18 ID_AC_WORKING. Новый код после успешной собственной климатической
команды ждёт первые 400 мс существующего readback, затем ОДИН раз отправляет
/9=2. Не затрагивает /18, /51 (PM2.5) и /64 (ароматизация). После этого только
читает /9 вместе с обычным обратным чтением, без повторов параметра или флага.

Служебный сброс отделён от публичного whitelist исполнительных команд.
Он не вызывается при запуске/опросе/уходе с экрана, для шторки, после ошибки
основной команды, без разрешения записи или после смены эпохи сессии.
Ошибка самого сброса записывается отдельно и не выдаётся за ошибку уже
выполненной климатической команды. Отключение/остановка OEM-сервиса не применяется.
Видимость физического окна по Binder НЕ подтверждается. Возможность краткого
первоначального появления и фактическое снятие флага требуют полевой проверки.

Локальные первичные источники в рабочей папке исследования:

- system-jadx/carlan/.../event/id/carlan/bean/VDNetworkStatus.java — INFO и Parcel;
- system-jadx/carlan/.../manager/b/a.java, метод b(TBoxNetworkStatus) — шкала GET;
- hvac-current-20261018/jadx/.../service/HvacService.java — CLOSE_HVAC_BT и /9=2;
- hvac-current-20261018/jadx/.../view/b.java — l()/n(), повторное открытие;
- system-jadx/carinfo/.../project/carinfo/HvacID.java — различие /9 и /18.

## Температура шин: остаётся нерешённой

В свежем журнале INFO /140 содержит [171,167,168,167], четыре канала давления.
Температурного вектора в этом ответе нет. В доступном SDK /143 — единица
температуры, /144 — предупреждения температуры/давления, /141 — яркость
окружения. Присваивать им градусы или подставлять DEMO было бы ошибкой.
Фото приборки доказывает наличие датчиков, но не способ чтения их данных
обычным Android APK. Нужно восстановить отдельный канал OEM/MCU; текущая версия
не заявляет эту часть исправленной. Отрицательный Android-тест проверяет, что
/143 и /144 не превращаются в реальные температуры.

## Проверки и установка

Сборка и 85 unit-тестов успешны. Полный Android-прогон: OK (65 tests),
0 ошибок, 145.182 с; журнал artifacts/qa-0.6.6-android.txt.
В том числе проверены OEM-ключ info и ошибочный data, нормализованный уровень
и отвергаемый RAW26, один сброс /9 без повтора климата, отмена сброса при pause/
блокировке записи, отсутствие повторов после ошибки сброса. Снимки синтетических
индикаторов в обеих темах: screenshots/qa-0.6.6/header-dark.png, header-light.png.
Все локальные Binder-тесты используют только фиктивные сервисы в памяти.
Проверки выполняются на BlueStacks 127.0.0.1:5555, не на автомобиле.

1. START → 1 → выбрать JelandOS-0.6.6-field-fixes.apk. Обновление поверх старой
   версии, без удаления приложения и настроек.
2. На стоянке включить интеграцию с ГУ и разрешить команды. Проверить температуру,
   вентилятор и AUTO по одной команде, подождать 4–5 секунд. Штатная панель не
   должна циклически открываться. Проверить, что реальные изменения сохраняются.
3. Отдельно проверить питание климата и сиденья. Скрытие окна не должно менять
   климат, питание или другие выбранные параметры.
4. Штатными настройками включить Wi-Fi и подключить известную сеть; вернуться
   в OS. Проверить BT выключен / включён без телефона / подключённый BT-телефон.
   CarPlay может не удерживать BT-профили и не считается BT-аудиосоединением.
5. Сопоставить 4G/полоски с OEM, затем собрать START → L. Нужны записи
   TBOX_CACHE, RADIOS, HVAC_UI_DISPLAY_CLEAR и GET 0x5000a/9.
6. Температура шин в этой версии всё ещё «Нет данных», а не вымышленные числа.
